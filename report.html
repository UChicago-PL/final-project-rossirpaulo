Overview

HaskProto is a schema-driven binary serialization system written entirely in Haskell. Given a human-readable .hproto schema file, it can parse, validate, and pretty-print the schema; encode structured data from JSON into a compact binary wire format; and decode binary data back into JSON. The system demonstrates a broad range of functional programming concepts from the course, including parser combinators, algebraic data types, and monad transformers.

Architecture

The project is structured as a Cabal package with two components: a library (seven modules) and an executable (CLI tool).

Technical Details

1. Schema Parser (HaskProto.Parser)

The .hproto parser uses Text.ParserCombinators.ReadP, the parser combinator library covered in the course material. It parses message definitions containing named, typed, tagged fields with optional modifiers (optional, repeated). The parser uses <$> for functor mapping, *> for sequencing with discarded results, (<++) for left-biased choice, and munch/munch1 for efficient character-class scanning. Message names must be capitalized; field names must begin with a lowercase letter.

2. Schema Validation (HaskProto.Validate)

After parsing, the schema is validated for five categories of structural errors: duplicate message names, duplicate field names within a message, duplicate field tags within a message, unresolved type references, and invalid (non-positive) tags. The validator collects all errors rather than stopping at the first, using Data.Map for counting occurrences and Data.Set for efficient membership checks during reference resolution.

3. Dynamic Values (HaskProto.Value)

Since Haskell's type system does not allow generating new types at runtime, HaskProto works with a dynamic value representation: 

data Value
  = VInt32 Int32    | VInt64 Int64
  | VUInt32 Word32  | VUInt64 Word64
  | VBool Bool      | VDouble Double
  | VString String  | VBytes [Word8]
  | VMessage [(String, Value)]
  | VRepeated [Value]
  | VNull

Helper functions (lookupField, hasField, messageFields, repeatedValues) provide typed inspection of values without requiring pattern matching at every call site.

4. Binary Wire Format (HaskProto.Wire)

The encoding follows a tag-length-value (TLV) wire format inspired by Protocol Buffers. Each field is prefixed by a key that encodes the field's tag number and wire type: 

field key = (tag << 3) | wire_type

Wire type 0 (Varint):  int32, int64, uint32, uint64, bool
Wire type 1 (64-bit):  double
Wire type 2 (Len-del): string, bytes, nested messages

Varint encoding stores unsigned integers using 7 bits per byte, with the MSB as a continuation flag. This is space-efficient for small values: the number 150 takes two bytes instead of four.

ZigZag encoding maps signed integers to unsigned ones so that values near zero (positive or negative) produce small varints. For example, −1 maps to 1, 1 maps to 2, −2 maps to 3, and so on.

Nested messages are encoded recursively: the inner message is serialized first, then written as a length-delimited field.

5. Monad Transformer Stack

Both the encoder and decoder operate in an MTL monad transformer stack that combines three effects: 

type EncodeM a = StateT [Word8] (ReaderT SchemaCtx (Except WireError)) a
type DecodeM a = StateT [Word8] (ReaderT SchemaCtx (Except WireError)) a
  • StateT [Word8] — accumulates output bytes during encoding; tracks remaining input bytes during decoding
  • ReaderT SchemaCtx — provides read-only access to the schema context (a map from message name to definition), threaded implicitly to all encode/decode functions via ask
  • Except WireError — structured error handling for type mismatches, truncated input, unknown messages, and invalid wire types

The public API unwraps the stack cleanly: 

encodeMessage :: Schema -> String -> Value -> Either WireError [Word8]
decodeMessage :: Schema -> String -> [Word8] -> Either WireError Value

6. JSON Integration (HaskProto.Json)

JSON parsing and rendering are handled by the aeson library, the standard Haskell JSON package. The module provides thin wrappers (parseJson, renderJson) that convert between String and Data.Aeson.Value, plus conversion functions (valueToJson, jsonToValue) that bridge between aeson's Value and our own dynamic Value type.

Schema-guided conversion is the key design decision: a raw JSON number like 7 is ambiguous (it could be int32, uint64, double, etc.), so jsonToValue consults the SchemaCtx to determine the correct Value constructor for each field. The conversion functions pattern-match on aeson's constructors (Object, Array, String, Number, Bool, Null) and use Data.Scientific for safe numeric coercions.

7. Testing

The proposal planned a QuickCheck test suite with property-based roundtrip tests. In practice, building a comprehensive automated test suite proved more extensive than anticipated: it would require custom Gen generators for every schema shape, careful handling of floating-point precision in JSON roundtrips, and a test harness wiring together the full encode/decode pipeline. This remains as future work.

That said, correctness was verified through deliberate manual debugging. This process uncovered two real bugs: reversed ordering of repeated fields during decoding (caused by insertWith (++) prepending instead of appending), and a failure to handle JSON null for optional fields during schema-guided conversion. Both were fixed by tracing through the encode/decode pipeline with the example schema and data.

8. CLI Tool (app/Main.hs)

The command-line interface exposes three subcommands: 

haskproto validate <schema.hproto>
haskproto encode <schema> <Message> <input.json> <output.bin>
haskproto decode <schema> <Message> <input.bin>

validate parses and checks a schema, reporting all errors or pretty-printing the result. encode reads JSON, converts it to a Value using the schema for type guidance, and writes binary. decode reads binary, reconstructs a Value, and prints JSON to stdout.

Example: End-to-End Roundtrip

Given this schema (examples/person.hproto):

message Person {
  name: string          @1
  age: int32            @2
  email: optional string @3
  addresses: repeated Address @4
}

message Address {
  street: string  @1
  city: string    @2
  zip: string     @3
}

And this input (examples/person.json):

{
  "name": "Paulo",
  "age": 24,
  "email": "paulorossi@uchicago.edu",
  "addresses": [
    {
      "street": "5454. S. Shore Dr., Apt. 1012",
      "city": "Chicago",
      "zip": "60615"
    },
    {
      "street": "R. Inhambu 66",
      "city": "Sao Paulo",
      "zip": "04520010"
    }
  ]
}

Encoding produces a compact 121-byte binary file (vs. 298 bytes of JSON, a 2.5× reduction):

$ cabal run haskproto -- encode examples/person.hproto Person \
    examples/person.json examples/person.bin

$ wc -c examples/person.bin
     121 examples/person.bin

Decoding recovers the original data:

$ cabal run haskproto -- decode examples/person.hproto Person examples/person.bin
{"addresses":[{"city":"Chicago","street":"5454. S. Shore Dr., Apt. 1012",
 "zip":"60615"},{"city":"Sao Paulo","street":"R. Inhambu 66",
 "zip":"04520010"}],"age":24,"email":"paulorossi@uchicago.edu",
 "name":"Paulo"}

(Output above is wrapped for display; the actual output is a single line of compact JSON.)

Concepts Employed

Concept Where / How
Algebraic Data Types Schema AST (Schema, MessageDef, FieldDef, FieldType, PrimTy, Modifier), dynamic Value, WireError, ValidationError
Parser Combinators (ReadP) Hand-written parser for .hproto schemas
Monad Transformers (MTL) StateT/ReaderT/Except stack for both encoding and decoding
State Monad Byte accumulation (encode), byte consumption (decode)
Reader Monad Schema context threaded implicitly through encode/decode via ask
Error Handling Except WireError for structured encode/decode errors; Either String for JSON conversion
Type Classes Show, Eq, Ord across all ADTs
Higher-Order Functions map, mapM, mapM_, concatMap, foldl, foldr, filter throughout
Pattern Matching Pervasive: wire type dispatch, value encoding/decoding, JSON conversion, field modifier handling
Bitwise Operations Varint encoding/decoding, ZigZag encoding, field key construction, IEEE 754 double conversion
Data.Map / Data.Set Schema context lookup, validation duplicate detection, decoded field accumulation

Deviations from the Proposal

  • Binary accumulation: uses [Word8] lists instead of ByteString.Builder. Simpler and clearer for the message sizes involved; bytestring is only used for file I/O in the CLI.
  • Value type: uses String and [Word8] instead of Text and ByteString, keeping the implementation consistent with the rest of the course material.
  • Automated testing: the proposal planned QuickCheck roundtrip properties, but building a comprehensive property-based test suite turned out to be more extensive than expected. Correctness was instead verified through deliberate manual debugging.
  • Schema evolution: not implemented. Of the Challenge goals, nested message encoding is done but the evolution engine, cross-version decoding, and inspect subcommand remain as future work.

Lessons Learned

  • ReadP is effective for custom grammars. Writing the .hproto parser with ReadP demonstrated how a small set of combinators (char, string, munch, (<++), sepBy, option) can handle a complete grammar. For standard formats like JSON, using a proven library like aeson is the right choice.
  • The MTL stack pays off. Threading the schema context via ReaderT and error handling via Except meant that individual encode/decode functions could focus purely on their logic. Adding a new primitive type required changes in exactly two places (encode and decode pattern matches), with the plumbing handled by the monad stack.
  • ZigZag encoding is elegant. The mapping zigzag(n) = (n << 1) xor (n >> 63) is a single-line function that makes varints efficient for signed values near zero. It is a great example of how bit-level thinking and high-level Haskell work together cleanly and elegantly.
