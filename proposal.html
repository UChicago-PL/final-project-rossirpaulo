HaskProto: A Schema-Driven Binary Serialization System

CMSC 22300 — Functional Programming — Winter 2026
Paulo R. Rodrigues — Solo Project

Overview

HaskProto is a simplified, Haskell-native take on the ideas behind Protocol Buffers. The system provides a human-readable schema language for defining structured message types, a parser that compiles schemas into an internal AST, a binary encoder/decoder that serializes and deserializes dynamic values according to those schemas, and a schema evolution engine that can diff two schema versions and determine whether they are wire-compatible.

I've been wanting to write something like this for some time, and it will allow me to exercise a broad range of the functional programming concepts introduced in this class; notably, parser combinators, algebraic data types, type classes, monad transformers, foldable/traversable, monoids, and property-based testing.

Schema Language

Users write .hproto files in a deliberately simple format. A schema consists of one or more message definitions, each containing typed, optionally tagged fields: 

message Person {
  name: string          @1
  age: int32            @2
  email: optional string @3
  addresses: repeated Address @4
}

message Address {
  street: string  @1
  city: string    @2
  zip: int32      @3
}

Supported primitive types will include int32, int64, uint32, uint64, bool, string, bytes, and double. Fields can be qualified as optional or repeated (defaulting to required). The @n tag annotations assign stable numeric identifiers used in the wire format, mirroring the role field numbers play in Protocol Buffers for forward/backward compatibility.

Architecture

1. Schema Parser (HaskProto.Parser)

The schema language is parsed using Text.ParserCombinators.ReadP, the parser combinator library covered in Chapters 19–20. The parser produces a strongly-typed AST: 

data Schema = Schema [MessageDef]

data MessageDef = MessageDef
  { msgName   :: String
  , msgFields :: [FieldDef]
  }

data FieldDef = FieldDef
  { fieldName     :: String
  , fieldType     :: FieldType
  , fieldModifier :: Modifier
  , fieldTag      :: Int
  }

data FieldType
  = PrimType PrimTy
  | RefType String        -- reference to another message

data PrimTy = TInt32 | TInt64 | TUInt32 | TUInt64
            | TBool | TString | TBytes | TDouble

data Modifier = Required | Optional | Repeated

The parser leverages applicative style (<$>, <*>, *>, <*), munch/munch1 for efficiency, and (<++) for left-biased alternatives, all as discussed in the course material.

2. Schema Validation (HaskProto.Validate)

After parsing, the schema undergoes validation: checking for duplicate message names, duplicate field names within a message, duplicate or missing tags, unresolved type references, and circular required-field references. Validation runs in an error-accumulating monad (ExceptT [ValidationError] Identity) and uses Traversable to walk the schema AST, collecting errors via a monoid.

3. Dynamic Values (HaskProto.Value)

Since Haskell's type system does not allow us to generate new types at runtime, HaskProto works with a dynamic value representation: 

data Value
  = VInt32 Int32
  | VInt64 Int64
  | VUInt32 Word32
  | VUInt64 Word64
  | VBool Bool
  | VString Text
  | VBytes ByteString
  | VDouble Double
  | VMessage [(String, Value)]
  | VRepeated [Value]
  | VNull                       -- for absent optional fields

A Serializable type class provides encode and decode operations that are schema-aware.

4. Binary Wire Format (HaskProto.Wire)

The encoding is a tag-length-value (TLV) wire format inspired by Protocol Buffers. Integers use variable-length encoding (varints). The encoder/decoder operates in a monad transformer stack: 

type Encode a = StateT BuilderState (ReaderT Schema (Except EncodeError)) a
type Decode a = StateT ByteOffset   (ReaderT Schema (Except DecodeError)) a

This naturally demonstrates the MTL pattern from Chapter 21: StateT tracks the current position in the byte stream, ReaderT provides the schema context needed to interpret tags, and ExceptT handles encoding or decoding errors. Binary output is accumulated using ByteString's Builder monoid.

5. Schema Evolution (HaskProto.Evolution)

A key feature is the ability to compare two versions of a schema and determine their compatibility. The evolution engine diffs schemas and classifies changes: 

data Change
  = FieldAdded FieldDef
  | FieldRemoved FieldDef
  | FieldTypeChanged FieldDef FieldDef
  | FieldModifierChanged FieldDef FieldDef
  | MessageAdded MessageDef
  | MessageRemoved MessageDef

data Compatibility
  = FullyCompatible
  | BackwardCompatible
  | ForwardCompatible
  | Breaking

Compatibility rules follow the Protocol Buffers conventions: adding an optional field is backward-compatible, removing a required field is breaking, tag reuse with a different type is breaking, etc. The diff operation uses Foldable to reduce schemas to maps keyed by tag number, then compares structurally.

6. CLI Tool (HaskProto.Main)

The user-facing interface is a command-line tool with the following subcommands: 

haskproto validate schema.hproto          -- parse and validate a schema
haskproto encode schema.hproto data.json  -- encode JSON data to binary
haskproto decode schema.hproto data.bin   -- decode binary back to JSON
haskproto diff old.hproto new.hproto      -- check schema compatibility
haskproto inspect data.bin                -- hex dump with field annotations

JSON is used as a convenient human-readable interchange format for constructing and inspecting dynamic values. The aeson library handles JSON parsing, while the .hproto parser is entirely hand-written using ReadP.

Tiered Goals

Easy (Core deliverable)

  • Parse .hproto schemas into an AST using ReadP
  • Validate schemas (duplicate names, unresolved references, tag conflicts)
  • Pretty-print schemas back from the AST
  • Define the dynamic Value type and basic construction/inspection

Medium (Expected deliverable)

  • Binary TLV encoding and decoding with varint support
  • Full monad transformer stack for encode/decode
  • JSON <--> Value <--> Binary roundtrip pipeline
  • QuickCheck properties for encode/decode roundtrips
  • CLI tool with validate, encode, decode subcommands

Challenge (Stretch goals)

  • Schema evolution: diff two schemas, classify compatibility
  • Cross-version decoding: decode data written with an older schema using a newer one
  • inspect subcommand: annotated hex dump of binary data
  • Nested message encoding with recursive schema support
