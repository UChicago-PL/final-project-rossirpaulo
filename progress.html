HaskProto: Progress Report

CMSC 22300 — Functional Programming — Winter 2026
Paulo R. Rodrigues — Solo Project

Summary

All Easy (Core deliverable) milestones from the proposal are complete and working. The project currently parses .hproto schema files into a strongly-typed AST, validates them for structural errors, pretty-prints them back to text, and defines a dynamic Value type for runtime representation of schema-typed data. A CLI tool with a validate subcommand ties these pieces together.

The codebase compiles with zero warnings under ghc-options: -Wall.

What Is Done

1. Schema AST (HaskProto.Schema)

Defines the core algebraic data types that represent a parsed schema: Schema, MessageDef, FieldDef, FieldType, PrimTy, and Modifier. These types mirror the structure proposed, with all eight primitive types (int32, int64, uint32, uint64, bool, string, bytes, double) and three field modifiers (Required, Optional, Repeated).

2. Schema Parser (HaskProto.Parser)

A hand-written parser using Text.ParserCombinators.ReadP, as covered in the course material. The parser handles the full .hproto syntax: message definitions with named fields, type annotations, modifier keywords, and @n tag numbers. It uses <$> for functor mapping, *> for sequencing with discarded results, (<++) for left-biased choice, and munch/munch1 for efficient character-class scanning.

Example input that parses successfully:

message Person {
  name: string          @1
  age: int32            @2
  email: optional string @3
  addresses: repeated Address @4
}

message Address {
  street: string  @1
  city: string    @2
  zip: int32      @3
}

3. Schema Validation (HaskProto.Validate)

Checks a parsed schema for five categories of errors:

  • Duplicate message names
  • Duplicate field names within a message
  • Duplicate field tags within a message
  • Unresolved type references (a field referencing a message name that does not exist in the schema)
  • Invalid tags (non-positive tag numbers)

Validation collects all errors rather than stopping at the first, returning them as a list. Duplicate detection uses Data.Map for counting occurrences, and reference resolution uses Data.Set for efficient membership checks.

4. Pretty Printer (HaskProto.Pretty)

Reconstructs .hproto text from the AST, producing clean, indented output. This serves as a roundtrip check: parse a file, pretty-print the result, and confirm it matches the original structure.

5. Dynamic Values (HaskProto.Value)

Defines the Value algebraic data type with constructors for all eight primitive types, message values (association lists of field name/value pairs), repeated values (lists), and VNull for absent optional fields. Provides helper functions for field lookup and inspection: lookupField, hasField, messageFields, and repeatedValues.

6. CLI Entry Point (Main)

A command-line tool that currently supports: 

haskproto validate schema.hproto

This parses the given file, runs validation, and either reports errors or prints the validated schema in pretty-printed form.

Example Session

Validating a correct schema:

$ cabal run haskproto -- validate examples/person.hproto
Schema is valid.

Pretty-printed:
message Person {
  name: string @1
  age: int32 @2
  email: optional string @3
  addresses: repeated Address @4
}

message Address {
  street: string @1
  city: string @2
  zip: int32 @3
}

Validating a schema with errors:

$ cabal run haskproto -- validate examples/bad.hproto
Validation errors:
  - DuplicateFieldName "Person" "name"
  - DuplicateTag "Person" 1
  - UnresolvedTypeRef "Person" "addr" "Nowhere"

Next Steps

The immediate next step is implementing the binary wire format (HaskProto.Wire). This will involve:

  • Variable-length integer (varint) encoding and decoding
  • A tag-length-value (TLV) wire format where each field is prefixed by its tag number and wire type
  • A monad transformer stack (StateT/ReaderT/ExceptT) for threading byte offsets, schema context, and error handling through the encoder and decoder

After the wire format is working, the plan is to add JSON integration (using aeson) for a full JSON → Value → Binary → Value → JSON roundtrip, followed by QuickCheck property tests to verify the roundtrip invariant.
